# 反过度防御黑名单：4 条第一性原理 + 母题主表

> 本文件是架构设计、编码实现与代码审查的核心标尺：先用 **4 条第一性原理**拷问每一处设计和改动，再对照 **15 个母题（A～O）** 的识别信号查漏。每个母题末尾列出案例编号，具体代码形态与事故复盘见 [blacklist-cases.md](blacklist-cases.md)（140 项案例库），按编号按需检索，不必通读。
>
> **母题和案例都不是穷尽清单。** 编码者与大模型会不断换花样（发明新的状态标记位、给确定性同步流程加假回调、把单次 SQL 拆成内存二次 join、给受控枚举加静默 `default:` 分支、用看似优雅的 helper 掩盖重复遍历……）。严禁只做机械勾选：抓住新花样靠的是 4 条第一性原理拷问，母题只是帮你更快认出老面孔。

## 一、4 条第一性原理拷问

对每一处设计和每一行改动主动过筛：

1. **存在性拷问（删掉会怎样？）**：如果删掉这行判空、分支、默认参数、拷贝、类型转换、包装函数或这段计算，在**真实生产调用链与真实数据契约**下，有任何合法输入或真实异常场景的行为会改变吗？不会（或触发条件根本穿不过上游边界），它就是伪装成“稳健”的废代码，立即删掉。
2. **单一事实源拷问（上游是不是已经算过/查过/证过了？）**：这个值、存在性保证、排序顺序、时间区间或解析产物，在同一个请求/事务/快照/渲染作用域的上游是不是已经拿到了？拿到了就显式传下来复用，不在下游再查、再转、再验，也不靠偷塞属性、改字典暗中传递。
3. **信任边界拷问（这是外部不可信边界，还是内部受控结构？）**：面对的是**首次进入系统的外部输入/跨请求存储边界**，还是**本进程刚刚构造或已通过边界校验的内部受控结构**？外部边界只校验一次，但要校验到位；对内部受控结构写容错兜底、反射探测（`getattr`/`hasattr`）、防御拷贝、宽泛 `except` 或事后自检，本质上都是掩盖缺陷的防御性垃圾。
4. **语义保真拷问（这一步之后，合法数据的意思变了吗？）**：每次比较、合并、过滤、去重、截断、归一化、降级、缓存回退或状态切换之后，问：合法的 `0`、`[]`、`False` 还是它自己吗？两个不同的身份还是两个吗？点事件、多段区间、复合枚举、模式切换这些特殊形态还在吗？校验看到的是完整关系闭包，还是一个切片？失败、取消、完成的每条分支都把状态复位了吗？前三条拷问抓“多做了”，这一条抓“做错了”；删防御时也靠它确认删掉的不是真实的业务保护。

## 三、母题详解（按主要违反的拷问分组）

每个母题写明识别信号（在 diff 或源码里看到什么就该警觉）、正确做法、两个典型例子和案例编号；`#27.1` 表示案例库第 27 条第 1 点。

### 拷问 1：删掉没有影响（多做了）

#### A. 死分支、死参数、伪可选
- **识别信号**：生产不可达的 `|| ''`、`or {}`、`if x is None` 分支；上游入口 100% 必传的参数（如事务 `context`），下层内部函数却层层挂着 `=None` 默认值并写 `context.xxx() if context is not None else Repo(conn).xxx()` 伪独立回退链；所有调用点恒传同一常量的开关，或中间层先 `pop("strict_mode", False)` 丢弃不透传，导致下层默认参数常年跑在死降级轨上；业务只剩唯一实现或 Schema 版本后，仍跨层保留 `source_table` / `role` 幽灵参数与 `SchemaVersion < N` 旧库探针；先伪造哨兵上限常数（如 `start + 30d`）再立刻拿同一上限 `min()` 裁剪；围绕生产从不构造的“幽灵配置子段”或 0 写入的“幽灵元数据键”写全套白名单、`try/except` 解析器与恒值摘要字段；对所有生产实现都具备的协议方法写 `getattr(obj, "method", None)` 能力探测以迁就残缺测试桩，并从测试回退分支派生出生产永不触发的错误码与计数；签名收了参数却不读，或进门第一行就被同名变量覆盖；只写不读的字段、全局状态和收集器；用 `_ = unused` 骗过 linter；新旧参数并存，旧参数只服务永不触发的回退分支。
- **正确做法**：分支、参数、字段一并删掉；上游已传入子结构或上下文时，直接改为必填参数，同步删掉原来的大容器参数和伪回退分支。
- **例子**：`#33` 新增 `w_timeline=None` 却保留 `worker_timeline`，再写永不触发的 `if w_timeline is None: w_timeline = worker_timeline.get(...)`，让两个参数在静态检查里都显得“被用到”；`#42` 签名照收 `metrics_by_id`，进函数第一行就被 `prepared["metrics"]` 同名覆盖。
- **案例**：#2、#17、#18、#19、#21、#28、#30、#33、#39、#42、#67、#114、#116、#117、#118、#119、#124、#126、#128、#130、#132、#136、#138

#### B. 多余的层
- **识别信号**：只有一个生产调用点的包装函数，拆开参数传进去后又跟原对象做同义比对；单调用方函数把底层的 `None` 变成 `raise`，唯一调用方紧接着 `try/except` 接住又变回 `None`；下层基类多写了一行读取侧 `.strip()`，上层不修基类反而专门派生单方法子类覆写同一方法绕开 `.strip()`；生产只有唯一策略或唯一表，却保留跨层表名分发器、`(version, source_table)` 二元组缓存键或只赋一行响应头的 `_response` 二传手包装；没有子类覆写的一行“扩展钩子”；搬家后原位置留下纯重导出模块、同义别名或层层垫片；对已缓存的属性再包一层 `@cached_property` 传话筒；热循环里为一次调用现造闭包；为迁就旧签名造内存伪仓储、现造单键字典、往元组里塞哑元 `0`。
- **正确做法**：一次性迁移全部调用点，删掉中间层；基类有契约毛病直接修基类，不派生绕路子类；接口不合适就改接口（让下层直接收上游现成的字典或标量），不在调用侧造适配。
- **例子**：`#48` 上游已有 `items_by_id`，却包成 `_ItemSnapshot` 伪仓储传下去，下层再调 `.list()` 重建同一个索引；`#12` `def has_table(conn, name): return table_exists(conn, name)`。
- **案例**：#4、#12、#20、#21、#31、#35、#36、#45、#48、#120、#125、#138、#139

#### C. 清理不彻底
- **识别信号**：删了上层服务、路由或导出出口，下层只为它服务的 Model、Repository、helper、事件采集列表、透传参数还在；多实现或多版本分支退役后，伴生的 0 引用旧查询仓储（如 `*_query_repo.py`）和跨层透传参数仍留在原地；在无静态作用域检查的 JS/JSX 组件中删了形参（如 `canNavigate`），只删了外层引用却把 `.map()` 循环体内的同名引用落在原地；读出口删了，模块级状态还在被写；为 0 调用的代码抽公共 helper，或把被删模块的依赖反向搬过来保活；把门禁台账当成保留理由；删了防御代码，注释和 docstring 还在吹嘘那层防御。
- **正确做法**：每删一处，顺着引用往下追，把引用数降到 0 的下层连根删掉；删 JS/JSX 形参后必须在该文件及构建产物里 `rg -n '\b<param>\b'` 确认残留为 0；台账项跟着死代码一起删；同步更新注释与文档。
- **例子**：`#30` 底层早已删了 `on_progress`，上面 5 层函数签名和进程间管道还在逐层透传；`#34` 不查调用方，就给 0 生产调用的死方法抽公共 helper。
- **案例**：#26、#30、#32.1、#34、#45、#97、#119、#124、#128、#129、#133、#134、#138

#### D. 靠测试续命
- **识别信号**：测试手工构造生产不可能出现的输入（如 `columns: []`、`start_time: 7`、空 `headline`）去跑通防御分支；测试原地 `.append()` 篡改返回值，证明防御拷贝删不得；测试拼出生产不存在的调用组合去覆盖死分支；测试的 `MagicMock` 漏配了真实返回结构（如应返回二元组 `(result, blocked)` 却返回单 `MagicMock`），全靠生产代码里的 `except Exception` 吞掉解包异常才显得测试全绿；为单个测试文件新建 `*_support.py`，绕过公开入口直调私有 `_legacy_*`；只改了文档却加 `readFileSync(...).includes(...)` 字面量测试；生产代码里留着只给测试用的 `.apply()`、monkeypatch 同步跳板、`fn is not _DEFAULT_FN` 身份比对。
- **正确做法**：先问“这条测试锁住的行为，生产里会发生吗？”；测试只走真实生产调用链和公开契约；夹具缺字段或返回值就补齐夹具；死代码连同只为它存在的测试一起删；纯文档改动不编字面量测试。审 diff 时 `tests/` 和生产代码一起看。
- **例子**：`#52` 为证明 `return list(self._rows)` 删不得，专门写测试 `rows.append(...)` 再断言；`#41` 生产已统一走 `prepare + apply_prepared`，类里还留着 0 生产调用的 `.apply()` 专供旧测试。
- **案例**：#2、#9、#27.5、#28、#39、#41、#43、#52、#118、#119、#129、#130、#134

#### E. 先算后扔
- **识别信号**：先把所有分支、所有行的重型结果算完，出口再用 `[]`、`_`、`[:K]` 抹掉或只取一个 `.total` 计数字段；准入或加载函数跑完重型归一化/事实构造后直接丢弃产物、只返回原始输入逼下游重算；不管有无待处理有效行，进门先无条件预建全表索引；导出格式、功能开关、空搜索词这类短路条件放在重型构造之后；先对全量做展示投影再筛选；缓存未命中检查写在依赖查询之后；`__init__` 里急切预跑重计算；生成器先构造重对象再去重；重试循环每轮都算只有终态才需要的量；有容量上限的读取在截断前让 SQL 全表排序。
- **正确做法**：按请求模式和实际消费按需计算；短路和筛选放在重型工作之前，筛选下推到最轻的原始事实层；终态才需要的量，命中终态再算。
- **例子**：`#58` 概览模式只看计数，却先构造全部 6 个分区的完整行列表，出口再抹成 `[]`；`#84` 页面只命中 20 行，却先对 5,000 行全量投影，再筛掉 4,980 行。
- **案例**：#6、#14、#58、#60、#61、#63、#73、#82、#84、#93、#135、#137

### 拷问 2：上游已经有了（重复做）

#### F. 重复校验
- **也涉及**：拷问 3。
- **识别信号**：上游边界或前一步已经保证的条件，下游又用 `if`、`.get()`、`isinstance`、`getattr`/`hasattr` 查一遍；为绕开 `getattr` 扫描，对本模块或上游受控链路刚产出的固定键字典连写 `row.get(k, default)`；准入函数校验即丢弃，导致下游拿到原始输入把完整归一化再跑第二遍；刚构造完立刻自检；一次业务动作里同一种全量校验跑两遍以上；内层组件已有守卫或事务，外层再包一层同职责守卫；模块导入时自检本文件写死的常量；SQL 聚合必返回一行非空值，Python 还要三重判空；渲染或万次循环里逐次重验上游契约。
- **正确做法**：校验只归属唯一的边界；内部直接索引必有键、直接复用前一步的返回值；自有类的属性在 `__init__` 或 dataclass 里显式声明。注意区分“全形态必有键”和“按判别字段区分的多态字典”：先判别分支，再索引该分支的必有键。
- **例子**：`#57` `validate_candidate()` 刚跑完全套约束，隔 4 行又对同一份入参调 `validate_commit_payload()` 从头重跑；`#10` 对本仓库自己的类写 `getattr(capture, "execution_service", None)`。
- **案例**：#1、#4、#10、#13、#22、#23、#25、#27.2、#49、#53、#56、#57、#62、#80、#89、#113、#114、#117、#118、#119、#121、#123、#124、#128、#132、#134、#135、#136

#### G. 重复计算
- **识别信号**：同一作用域重复扫描、重复建索引、重复 `PRAGMA` 或元数据查询；加载/准入函数内部已构造重型事实对象却不随返回值带出，逼多个调用方紧接着各自再构造一遍；只取计数或前 K 条摘要却走全量分页投影；已有批量预取方法，分页/列表循环前却漏调预取退化为逐行 N+1；同一事务先探测再取数，或路由穿透私有方法把服务里刚跑过的查询再跑一遍；同一个请求对象跨层实例化、`coerce` 好几遍；循环里重算与循环变量无关的值，或每轮重建外层列表、重复 `sorted()`；静态常量表每次调用都线性遍历；已有预计算读模型，却去碰会触发全量反序列化的冷路径属性；查询条件写法让 SQLite 放弃索引、反复全扫。
- **正确做法**：同一作用域算一次、查一次，显式传下去复用；进入分页/列表循环前先按本页键集调用批量预取；不变量提到循环外或模块加载期；Service 公开方法一次返回调用方需要的全部结果；展示与筛选链路只从读模型取数。
- **例子**：`#80` 路由先调 `service.preview_export()`，下一行又穿透调私有 `service._states_and_rows()`，把同样的查库重跑一遍；`#15` 先 `find_by_request_key()` 拿 `job_id`，下一行再 `get_status(job_id)` 查同一条记录。
- **案例**：#5、#8、#14、#15、#22、#23、#48、#68、#70、#80、#89、#95、#96、#97、#101、#123、#135、#137

#### H. 缓存失效
- **识别信号**：缓存键混入每行唯一 ID 或与结果无关的可变字段（命中率 0%，或改一行全盘失效）；以 `id(obj)` 为键，热路径却每轮 `copy(obj)`；命中后原地回写，或命中后仍无条件全量扫描、排序、归档；外层派生缓存和底层按需加载缓存各存一份、互不同步；用 `or` 判断缓存值是否存在，合法的 `0`、`[]` 被当成缺失；把整份派生结果塞进快照指纹做序列化；缓存异常实例后多次裸 `raise cached_exc`，导致 `__traceback__` 栈帧成倍累积。
- **正确做法**：缓存键只含真正决定结果的输入；命中就短路；二级索引内聚在唯一事实源对象里，随加载原子更新；判断“已提供”用 `is not None` 或 `key in cache`；指纹只绑定源头版本和查询边界；重抛缓存的异常实例前用 `.with_traceback(None)` 清掉旧栈帧。
- **例子**：`#65` `window_key = (task_id, start_dt, due_dt)`，每条任务一个键，5,000 条任务命中率恒为 0%；`#83` 命中去重缓存后，仍对 5,000 个结果对象全量扫描、排序、重新归档。
- **案例**：#21、#60、#61、#64、#65、#78、#81、#83、#85、#101、#105、#113

#### I. 偷偷传状态
- **识别信号**：把数据挂在函数对象属性上，再 `getattr(fn, ...)` 取出来；从外部函数往别人的服务、快照或解码器实例上塞 `_private` 私有属性，下游再用 `getattr(..., None)` 探测并配回库/重算兜底；在服务或仓储实例上临时赋值、`finally` 里置空来传参；往纯数据字典里塞服务或仓储实例（如 `facts["reader"] = reader`）；`@property.setter` 里藏同步副作用，正规更新方法里又手动同步一遍；两个视图共享同一批可变 dict，靠对其中一处原地改写“顺带”同步另一处。
- **正确做法**：用显式参数、返回值或 dataclass 传递；状态变更只有一个正规入口；不同视图的字段转换各自显式赋值，不靠共享可变对象原地改写隐式联动。
- **例子**：`#29` 在 `with service.read_snapshot():` 里偷偷给 `self.active_codes` 赋值，`finally` 又置回 `None`，逼调用方在退出前“抢救”；`#96` 调用前写 `repo.report_revisions = ...`，调用后在 `finally` 里清空。
- **案例**：#29、#40、#54、#96、#113、#122

#### J. 口径没在源头统一
- **识别信号**：同一条领域规则在表单入口和文件导入入口各写一套，或两处写着 `# Mirrors ...` 镜像注释各自维护同一套归类逻辑，且单函数内部又分快慢两段把同一判断写两遍；横切响应头（如 `Cache-Control: no-store`）不在底层响应工厂与路由装饰器统一设置，而在几十个路由里散落手写；共享底层文件读取器放任重复/倒序坐标覆盖、只在单个子域入口打补丁校验；把完全由其他字段决定的派生值存成 dataclass 可写字段，改源字段（如 `replace()`）后失步，靠下游冗余重转顺手纠正；大小预算守卫用默认 `json.dumps(obj)`（含空格且放行 `NaN`）丈量字节数，实际落库却写紧凑 `canonical_json(obj)`；预览和提交各算一遍，结果可能不同；多事件/分组账本已有领域归并函数，下游却逐条裸检单行字段；发现上游漏字段，在下游调用处手写推导式补；调用方自己切片，绕过被调函数的契约上限；两件职责塞进一个返回元组的 `Optional` 函数，调用点再用三元和 `lambda: fn(None)[0]` 绕；复合枚举已有能力谓词（如 `supports_mode`），某处却用原始值集合相等判断；加 `strict_*=False` 这类双轨开关，让同一种事有两套口径；跨文件复制粘贴同一段语义逻辑（甚至混入后端永不产出的“幽灵错误码”）。
- **正确做法**：规则与物理格式不变量抽到唯一的领域函数或共享读取边界，所有入口共用；纯派生值做成只读 `@property` 在源头实时计算，不存成可失步的冗余字段；预览和提交共享同一个状态转移结果；上游缺什么回上游补，删掉下游补偿；一个函数只承担一个职责。
- **例子**：`#55` “非工作日必须清空工作时段、配额设为 0”在详情表单里写一套，在电子表格导入里又拆成两段写一套；`#75` 导入预览算出一套目标集合，提交时却不消费预览结果、按行序重新算。
- **案例**：#8、#27.3、#31、#38、#54、#55、#59、#75、#81、#98、#99、#102、#106、#107、#108、#109、#115、#116、#117、#121、#123、#125、#131、#132、#139

### 拷问 3：把内部结构当外部输入防（防错了地方）

#### K. 吞错与静默降级
- **也涉及**：拷问 4。
- **识别信号**：内部受控计算外面包 `except (KeyError, TypeError, ValueError, ...)`；对自产受控字典写 `candidate.get("order") or self.current_order`，缺键时静默回退旧状态；把锁文件读取 `OSError` 与内容损坏混同降级，触发过期自愈误删活跃锁（Fail-Open）；`from_row` 用吞 `KeyError` 的 `get(row, key, default)` 掩盖多条 `SELECT` 漏选列或模型死字段；存储整数解析器给 `NOT NULL` 列配 `default=0/1` 并用 `bytes.decode("utf-8", errors="ignore")` 把损坏数据静默读成合法数字；`finally` 里关闭失败直接 `raise` 顶掉 `try` 块已拿到的结果，再被外层宽泛 `except` 张冠李戴归入其他原因；捕获后转成默认值、`None` 或笼统的“未证明”；底层已有明确的异常或回退契约，外层又包一层 `try`；同一函数里自己 `raise` 自己 `except`，或 `json.loads` 外层用 `except ValueError` 误吞 `object_pairs_hook` 抛出的业务拒绝异常；先塞默认值，再写永远进不去的 `if x is None: raise`；上下文损坏时降级成 `None`，反而绕过了针对它的业务限制；底层抢先抛笼统异常，或在调用存量结构守卫前先对未校验行跑 `sorted()`/推导，让 `TypeError` 抢跑炸穿结构化诊断；`LEFT JOIN ... continue` 把损坏数据当成没有数据。
- **正确做法**：`try` 只包解析外部输入或存储字节的最小语句，只捕精确异常（如 `json.JSONDecodeError`）；内部 `KeyError`、`TypeError` 是缺陷，让它暴露；`NOT NULL` 列解析不配 `default`，数据损坏就先走存量结构守卫明确拒绝，不降级也不让未校验排序抢跑；必填校验面对未兜底的原始输入。
- **例子**：`#47` `group = None if problem else build_group(context)`：上下文越坏，后面的 `if group and group["mode"] == "merged": raise` 越管不住；`#18` `parse_hhmm(..., allow_none=False)` 缺失时静默返回 `"08:00"`，下一行的 `if start is None: raise` 永远进不去。
- **案例**：#16、#18、#19、#32.2、#37、#47、#67、#92、#100、#103、#111、#115、#120、#126、#127、#130、#133、#136、#140

#### L. 删旧壳时搬家兜底
- **说明**：编码模型（尤其是 GPT）被要求删防御时最常见的反扑，审它改过的代码时重点查。
- **识别信号**：要求删掉一处兜底、吞错或包装后，diff 里下层反而冒出新的 `try/except`、`.get()`、`or default`、`is not None`、`Optional = None`；不敢统一口径，加 `strict_*=False`、`_prevalidated=False` 这类双轨开关；子类或测试夹具漏了必填属性，就在基类写 `if self.attr is not None else ...` 再配 `cast(...)`；拆函数时把旧代码的宽泛 `except` 原样抄进新函数。
- **正确做法**：删兜底就是删，按上游真实契约直接 `payload["key"]`、`obj.attr`；统一规则直接合成一个严格口径；缺的初始化补在子类或夹具里；搬迁函数时按新函数体重新判断真正可能抛出的异常。
- **例子**：`#27.1` 删掉上层 1 处宽泛 `except`，下层 5～7 个函数各塞一套，1 处吞错裂变成 7 处；`#44` 删掉包装模型后，在仓储里写 `payload.get("status") or "active"`，而唯一调用方早已传入完整字典。
- **案例**：#27.1、#27.3、#27.4、#37、#44

#### M. 无用拷贝与往返转换
- **也涉及**：拷问 2。
- **识别信号**：对不会被原地修改的受控数据做 `.slice()`、`list()`、`dict()`、`deepcopy()`、`asdict()`；上游构造器无脑 `[dict(row) for row in items]` 只为替下游某处原地修改擦屁股；用 `json.loads(json.dumps(x))` 当深拷贝；刚解析成 `datetime` 又 `.isoformat()`，下一层再 `fromisoformat()`；将原生 `int` 或纯整数字符串绕道 `float(value)` 往返转换导致 `> 2^53` 精度丢失；`set(list(set(...)))`；仓储已返回新 `dict`，上层再套 `[dict(row) ...]`；热路径每轮 `copy(obj)`。
- **正确做法**：入口解析一次，内部传强类型对象，只在最终输出边界转换一次；精确整数绝不绕道 `float`；只读访问器直接返回底层引用；需要重映射字段时由下游转换处生成新字典（谁转换谁负责），不在上游做防御性拷贝。
- **例子**：`#11` `parse_dt` 的结果立刻转成字符串返回，下一层算分钟差再 `fromisoformat()`；`#56` 只读列表的万行循环里每行两次 `json.dumps + json.loads` 往返，结果被唯一调用方直接丢弃。
- **案例**：#3、#11、#20、#23、#52、#56、#64、#107、#110、#122

### 拷问 4：意思被改了（做错了）

> 这一组和前三组方向相反：问题不是多做，而是做错。删防御、做统一时最容易顺手踩中，也最容易被误当成“过度防御”删掉。

#### N. 事务、锁与状态生命周期
- **也涉及**：拷问 2。
- **识别信号**：写锁或事务里做文件 I/O、纯内存建报表、大 JSON 哈希，或逐行 N+1 发号、反查；外层已持有事务，内层循环逐行开嵌套 `SAVEPOINT`，或刚断言“必须在事务内”又套一层事务；前置校验失败，却留下预设的终态标志、锁或 `PENDING_KEY`；把服务端已确认终态（成功回执或明确拒绝）后的本机存储写/删混进网络请求 `try/catch`，使本机存储异常将已知终态篡改成 `pending`/`lookup_failed`，或自动跟进探查进门无条件清空刚捕获的提交失败原因；靠上下文里是否已设置 `request_key` 反推请求是不是写操作，或未校验 `request_key` 格式就先写入上下文；删锁文件、杀进程这类破坏性动作先于参数检查，或锁文件读取 `OSError` 未走 Fail-Closed 反而进过期自愈分支把活跃锁删掉；禁用条件不区分 `pending`/`done`/`rejected`/`stale`，或唯一的解锁回调放在可能不挂载或被焦点陷阱锁在底层的组件里；单任务失败恢复时调用全表清理；`except BaseException` 误捕 `StopIteration`，或 `except Exception` 漏掉 `GeneratorExit` 导致不回滚；会话切换只重置一半状态。
- **正确做法**：事务边界只归一处，锁内只做必须在锁内的最小工作；批量操作用无事务包装的写入原语共享外层事务；失败、取消、完成的每条分支都对称复位预占状态；严格分离服务端命令终态与本机存储状态，明确拒绝后清理失败仍保持 `rejected` 供重试；读写职责由入口显式声明，`request_key` 校验合格后再绑定上下文；检查先于破坏性动作；清理函数显式绑定目标范围；子会话的全部状态与会话身份同生共死。
- **例子**：`#79` 恢复在前置检查阶段失败、原库没动，却没复位预设的 `restart_required=True`，宿主永久 503，用户无法重试；`#49` 批量入口已开事务并查过表结构，循环里每行又调单条入口，再开一层事务、再查一遍。
- **案例**：#7、#25、#49、#62、#66、#74、#79、#86、#87、#88、#104、#111、#112、#116、#127、#140

#### O. 语义走样
- **识别信号**：
  - 用 `or` 合并可能为 `0`、`[]`、`""` 的合法值；类型校验或归一化之前就用 `==` 比较、过滤“未改字段”（`True == 1`）；用 `float` 容差近似（`abs(f - round(f)) <= 1e-9`）代替 `Decimal` 精确整数解析，放行近似小数并截断大整数精度；稀疏导入把显式清除标记（如 `\N` 解码出的 `key: None`）与“留空未填（省略 `key`）”混同为保持原值；推导式里把业务子集过滤条件写在字段合法性校验前面，让被过滤掉的记录绕过校验；
  - 读取或引用侧对已落库的身份 `.strip()`，把 `" B1 "` 和 `"B1"` 合成一个；`a if a is not None else b` 让陈旧信号遮住存活信号；
  - 用 `segments[0]` 或首尾包络代替多段区间；零时长点事件混进区间重叠公式，或被 `end <= start` 一刀切拒绝；
  - 只取局部切片去做需要完整关系闭包的校验；先校验全量输入再 diff，没改的字段被误拒；先生成派生快照再改主键，或校验前用待测数据改写校验基准；后台异步执行不复用受理归档快照，反而重调挂钟时间 `date.today()` 导致跨午夜结果漂移；
  - 模式切换时拿旧模式的汇总列做同值过滤；生成器出口去重却不推进游标和预算计数；新一代引用表没纳入删除依赖统计；
  - 对可能混入 `bytes` 等降级类型的字段直接排序或 `json.dumps`；重抛 `ValidationError(..., details=exc.details)` 时只改顶层 `exc.field` 却原样透传旧 `details["field"]` 造成顶层与明细自相矛盾；正常业务边界（零配额、区间合并）混进“数据损坏”标记；把 `PRAGMA integrity_check == 'ok'` 当成备份有效（空库也返回 ok）。
- **正确做法**：判断“已提供”用 `is not None`；严格区分字典省略键（留空保持原值）与键值为 `None`（显式清除）；先对全量记录做字段合法性校验，再按业务条件过滤；先归一化、先验类型，再 diff；写入口严防、读与引用侧保真；多个信号源逐个评估；多段结构全程保持多段；校验按完整关系闭包取数；新身份在派生快照之前分配；异步执行直接消费受理归档快照；模式切换本身就是语义变更；去重在序列源头一次完成；正常边界和数据损坏分开标记。
- **例子**：`#94` 类型校验前写 `{k: v for k, v in values.items() if v != raw[k]}`，库存为 `1` 时上传 `TRUE` 被当成“没改”，绕过了布尔拒绝；`#91` 底层“防御性” `.strip()` 把对 `" W1 "` 的读写串到 `"W1"` 头上。
- **案例**：#24、#46、#50、#51、#68、#69、#71、#72、#75、#76、#77、#78、#81、#85、#90、#91、#92、#93、#94、#95、#98、#99、#100、#102、#104、#106、#107、#108、#109、#110、#112、#125、#126、#131、#132、#133、#134、#140

## 四、怎么用与入库规则

### 1. 怎么用
- 每处改动先过 **4 条第一性原理拷问**，再扫一遍 **15 个母题**的识别信号；对某个母题拿不准时，按编号去 [blacklist-cases.md](blacklist-cases.md) 看原始案例。
- 删防御之前，用**拷问 4** 和 **N、O 两个母题**确认删掉的不是真实的业务保护（快照一致性、完整关系闭包、旧事实保护等）。
- 审 diff 时同时审 `tests/` 的 diff（母题 D）。

### 2. 入库规则
抓到新花样时，先当场剥离，再按下面的规则入库：
1. **先归类**：对照母题的识别信号归类。能归进已有母题的，只在案例库末尾追加案例（编号顺延）并标注母题；如果它暴露了这个母题现有识别信号覆盖不到的写法，在主表这个母题的“识别信号”里补半句。
2. **归不进才新开**：哪个母题都归不进去，才新开母题，放进它主要违反的那条拷问分组下，写齐识别信号、正确做法、例子和案例编号。
3. **一条一事**：一条案例只写一种花样，互不相干的两件事分成两条；写清识别信号和正确做法，事故细节点到为止。
4. **主表保持精简**：每个母题最多两个例子；正文不写案例总数。
5. **能合就合**：发现两个母题其实是一回事就合并；案例库只改母题标注，不改编号。
