# 反过度防御黑名单：4 条第一性原理 + 母题主表

> 本文件是架构设计、编码实现与代码审查的核心标尺：先用 **4 条第一性原理**拷问每一处设计和改动，再对照 **15 个母题（A～O）** 的通用代码形态信号查漏。具体战例与事故复盘以 [blacklist-cases.md](blacklist-cases.md) 为唯一事实源（主表仅列代表案例，不手抄全量编号；按需检索，不必通读）。
>
> **母题和案例都不是穷尽清单。** 编码者与大模型会不断换花样（发明新的状态标记位、给确定性同步流程加假回调、把单次 SQL 拆成内存二次 join、给受控枚举加静默 `default:` 分支、用看似优雅的 helper 掩盖重复遍历……）。严禁只做机械勾选：抓住新花样靠的是 4 条第一性原理拷问，母题只是帮你更快认出老面孔。

## 一、4 条第一性原理拷问

对每一处设计和每一行改动主动过筛：

1. **存在性拷问（删掉会怎样？）**：如果删掉这行判空、分支、默认参数、拷贝、类型转换、包装函数或这段计算，在**真实生产调用链与真实数据契约**下，有任何合法输入或真实异常场景的行为会改变吗？不会（或触发条件根本穿不过上游边界），它就是伪装成“稳健”的废代码，立即删掉。
2. **单一事实源拷问（上游是不是已经算过/查过/证过了？）**：这个值、存在性保证、排序顺序、时间区间或解析产物，在同一个请求/事务/快照/渲染作用域的上游是不是已经拿到了？拿到了就显式传下来复用，不在下游再查、再转、再验，也不靠偷塞属性、改字典暗中传递。
3. **信任边界拷问（这是外部不可信边界，还是内部受控结构？）**：面对的是**首次进入系统的外部输入/跨请求存储边界**，还是**本进程刚刚构造或已通过边界校验的内部受控结构**？外部边界只校验一次，但要校验到位；对内部受控结构写容错兜底、反射探测（`getattr`/`hasattr`）、防御拷贝、宽泛 `except` 或事后自检，本质上都是掩盖缺陷的防御性垃圾。
4. **语义保真拷问（这一步之后，合法数据的意思变了吗？）**：每次比较、合并、过滤、去重、截断、归一化、降级、缓存回退或状态切换之后，问：合法的 `0`、`[]`、`False` 还是它自己吗？两个不同的身份还是两个吗？点事件、多段区间、复合枚举、模式切换这些特殊形态还在吗？校验看到的是完整关系闭包，还是一个切片？失败、取消、完成的每条分支都把状态复位了吗？前三条拷问抓“多做了”，这一条抓“做错了”；删防御时也靠它确认删掉的不是真实的业务保护。

> **源头治本提醒（保证交付定律）**：下游满屏 `.get()`、判空与无脑拷贝，往往是因为上游“只做放行检查，没交出结构字据”（验完仍传未定型裸 `dict`、持久层约束只写在写入口没落成 Schema `CHECK` 与唯一读取原语、写原语藏匿生成值、可变容器所有权不明）。删下游防御时，同步在源头把保证变成定型结构交出来，让下游防御彻底失去存在理由。

## 三、母题详解（按主要违反的拷问分组）

每个母题写明跨项目通用的**识别信号**（在 diff 或源码里看到什么结构就警觉）、**正确做法**和两个**代表例子**；`#27.1` 表示案例库第 27 条第 1 点。

### 拷问 1：删掉没有影响（多做了）

#### A. 死分支、死参数、伪可选
- **识别信号**：生产契约下不可达的 `|| ''`、`or {}`、`if x is None` 分支，或先伪造哨兵常数上限再立刻拿同一上限 `min()` 裁剪；上游 100% 必传的参数在下层内部函数挂 `=None` 并写伪独立回退链，或新旧参数并存、旧参数只服务永不触发的回退分支；所有调用点恒传同一常量的开关，或中间层 `pop` 丢弃开关不透传、让下层默认参数常年跑在死分支上；对所有生产实现都具备的协议方法写 `getattr(obj, "method", None)` 迁就残缺测试桩；签名收参却不读、进门第一行就被同名局部变量覆盖、或写 `_ = unused` 骗 linter；只写不读的僵尸字段、收集器与模块级状态；业务只剩唯一实现或唯一 Schema 版本后仍跨层保留的幽灵多态参数与旧版探针；持久化格式零变更却预设假想离线转换器，或无公网分发安全需求的单机项目中铺设仪式感哈希清单。
- **正确做法**：分支、参数、字段一并删掉；上游已传入子结构或上下文时直接改为必填参数，同步删掉原大容器参数和伪回退分支。
- **例子**：`#33` 新增 `w_timeline=None` 却保留 `worker_timeline`，再写永不触发的 `if w_timeline is None: w_timeline = worker_timeline.get(...)`，让两个参数在静态检查里都显得“被用到”；`#42` 签名照收 `metrics_by_id`，进函数第一行就被 `prepared["metrics"]` 同名覆盖。

#### B. 多余的层
- **识别信号**：单生产调用方的包装函数（拆属性传参再跟原对象自比对、前一步已验完紧接空转校验包装、单行响应头包装）；单调用方函数把底层 `None` 变 `raise`，唯一调用方紧接着 `try/except` 接住变回 `None`；不修基类契约缺陷（如多余的读取侧 `.strip()`），反而派生单方法子类覆写绕路；生产只剩唯一策略或唯一表，仍留跨层分发器；无子类覆写的 1 行“扩展钩子”；对已有缓存的属性再包一层 `@cached_property` 传话筒，或在热循环里为单次调用现造闭包；为凑旧签名造内存伪仓储、单键临时字典、`(val,)` 单元素元组包装或元组哑元；模块搬迁后原处留下纯重导出空壳、同义别名、层层垫片、无包级状态的 `__init__.py` 动态 `__getattr__` 桶文件，或保留旧原型目录靠复制脚本中转；不在自有 UI 组件模板源头输出语义属性，反而在外层挂副作用钩子事后扫 DOM 补属性。
- **正确做法**：一次性迁移全部调用点并删掉中间层；基类有契约毛病直接修基类；接口不合适就改接口（让下层直接收现成字典或标量），不在调用侧造适配。
- **例子**：`#48` 上游已有 `items_by_id`，却包成 `_ItemSnapshot` 伪仓储传下去，下层再调 `.list()` 重建同一个索引；`#12` `def has_table(conn, name): return table_exists(conn, name)`。

#### C. 清理不彻底
- **识别信号**：删了上层服务、路由或出口，底下只为它服务的 Model、Repository、helper、状态写入或旧物理目录仍留在原地（次生孤岛）；底层已删参数或内层已删重复校验，整条调用链仍在层层透传断头参数或恒空占位实参；替换底层查询或执行原语（如分片 `IN` 循环改为单次集合传参）后，原封不动保留旧原语时代用来控分片的排序、去重与空集守卫；在无静态作用域检查的 JS/JSX 组件中删了形参，只改外层却把 `.map()` 等内嵌回调里的同名引用落在原地；不查生产调用数就给 0 生产调用的死代码抽公共 helper，或反向迁入被删模块的依赖保活死函数；拿门禁台账或个别测试顺手 `import` 的两三个小函数为整份数千行退役脚本续命；防御代码已删，注释、docstring 和文档仍在描述那层防御。
- **正确做法**：每删改一处顺着引用追到底，把生产引用归零的下层及旧原语附带守卫连根拔除；删动态模板/JS 形参后在源码与构建产物中全文检索确认零残留；台账项随死代码同步移除，注释与文档一并更新。
- **例子**：`#30` 底层早已删了 `on_progress`，上面 5 层函数签名和进程间管道还在逐层透传；`#34` 不查调用方，就给 0 生产调用的死方法抽公共 helper。

#### D. 靠测试续命
- **识别信号**：测试手工捏造生产边界绝不会放行的非法输入、原地篡改后端受控返回值、或 `DROP TRIGGER` 塞脏值，只为证明死防御或死拷贝删不得；拼凑生产不存在的跨模式调用组合，或生产 100% 传 `None` 仅靠单测传常量给死分支续命；测试 `MagicMock` 漏配真实返回元组/字段，全靠生产代码里的宽泛 `except` 吞掉解包异常才显得全绿，或写单测断言内部浅拷贝调用次数反向锁死无用拷贝；生产类里留着 0 生产调用的旧入口（如一步式 `.apply()`）、monkeypatch 属性同步跳板、`_DEFAULT_FN` 身份比对专供旧测试，或为单测建孤立 helper 绕过公开入口直调私有 `_legacy_*`；只改了说明文档却加 `readFileSync(...).includes(...)` 字面量匹配测试。
- **正确做法**：先问“这条测试锁住的行为生产里会发生吗？”；测试只走真实生产调用链和公开契约，夹具残缺就补齐夹具；死代码连同只为它站台的测试一起删；纯文档改动不编字面量测试。审 diff 时 `tests/` 与生产代码一起看。
- **例子**：`#52` 为证明 `return list(self._rows)` 删不得，专门写测试 `rows.append(...)` 再断言；`#41` 生产已统一走 `prepare + apply_prepared`，类里还留着 0 生产调用的 `.apply()` 专供旧测试。

#### E. 先算后扔
- **识别信号**：先把全部分支、全量行的重型构图或展示投影算完，出口再用 `[]`、`[:K]` 抹掉或只取 `.total` 计数；仅针对勾选的少量实体做批量预览/删除/导出，却无条件加载全库整表再按主键过滤，或首屏接口无条件内联数 MB 低频明细触发超限；准入/核验阶段已完整读入文件或构造归一化产物却直接丢弃、只返原始输入，逼下游二次读盘（TOCTOU）或重算，写入原语已算出主键/时间戳/版本号却隐匿不返逼同事务调用方写后回读，或公开投影函数顺手 `.pop()` 删掉同事务后续步骤还要消费的内部字段；把旧快照 token 核验、导出格式、功能开关、空搜索词、预算评估等轻量短路条件放在重型查询/构造之后，或带 `LIMIT` 的查询在截断前做无索引全表排序；模块 `import` 顶层或 `__init__` 急切执行连库建表/重计算，重试循环每轮计算终态量，或对未入选样本无条件序列化算哈希；为取单个标量调用完整装配工厂再丢弃；门禁或缓存指纹用无后缀 `**/*` 把未跟踪草稿、字节码和历史副产物全量卷入读取。
- **正确做法**：按请求模式与目标实体闭包按需查询计算；读快照进门第一步先验轻量 token；核验阶段已读出的原文、解析产物及写入原语已确定的生成值显式返回或下传复用；轻量短路与筛选下推到重型工作之前；指纹通配符精确限定受控目录与扩展名。
- **例子**：`#58` 概览模式只看计数，却先构造全部 6 个分区的完整行列表，出口再抹成 `[]`；`#84` 页面只命中 20 行，却先对 5,000 行全量投影，再筛掉 4,980 行。

### 拷问 2：上游已经有了（重复做）

#### F. 重复校验
- **也涉及**：拷问 3。
- **识别信号**：上游边界或前一步已保证的条件，下游又用 `if`、`.get(k, default)`、`isinstance` 查一遍，或刚写完 `if x is None: return` 下一行紧跟 `assert x is not None`；对本仓库自有类用 `getattr`/`hasattr` 反射探测属性；刚确定性构造完局部结果立刻事后自检/自查找、往返还原比对，生产者写死恒真完整性标记（如 `complete=True`）再由下游专门校验该常量标记，或构造函数同时收 `parent` 与 `parent.child` 只为断言两者是同一个；同一业务动作跨路由/模型/服务连跑 2～3 遍同款校验，或内层组件已内聚守卫/事务、外层调用方再包一层同职责守卫导致副作用翻倍；单机前端对自家同进程后端刚返回的受控 DTO（含按请求原样回显的字段）写键数白名单、分页算术重验、全量 diff 重算与排序重验，或单机闭合库搞防元类/防篡改/跨表伪公证链/每事务验触发器 DDL/内部摘要正则脱敏；模块 `import` 时自检本文件写死的静态常量，或对必返单行非空值的 SQL 聚合套多重判空。
- **正确做法**：校验只归属唯一边界，准入即返回不可变定型结构，内部直接索引必有键并复用上游已验证返回值；自有类属性在 `__init__` 或 dataclass 中显式声明。区分“全形态必有键”与“按判别字段区分的多态字典”：先按权威判别字段分支，再直接索引该分支必有键。
- **例子**：`#57` `validate_candidate()` 刚跑完全套约束，隔 4 行又对同一份入参调 `validate_commit_payload()` 从头重跑；`#10` 对本仓库自己的类写 `getattr(capture, "execution_service", None)`。

#### G. 重复计算
- **识别信号**：同一请求/事务/快照/渲染作用域内重复扫描、重复建索引、重复解析同一批时间字符串或百万字节 JSON，或路由穿透私有方法重跑服务刚查过的查询；同一事务内“先探测存在再二次查库取同一行”、写入原语藏匿生成值逼调用方紧接 `SELECT` 写后回读，或同一连接连发相同 `PRAGMA`/元数据查询；已有批量预取、共享缓存或预计算读模型，下游却漏调预取退化为 N+1、多处旁路绕过缓存各自重建、或误触冷属性触发全量反序列化；循环内重复计算与循环变量无关的量（未预编译正则、每次新建解码器/闭包、重复 `sorted()`、静态常量表线性遍历），或二元计算任一入参为 `None` 时不提前短路；数据结构或 SQL 写法退化（含早期长包络区间的交集查询用单调前缀伪二分退化回 100% 线性全扫、高频双层字典查找套慢速 `ChainMap` 生成器、查询条件令索引失效）。
- **正确做法**：同一作用域算一次、查一次，显式传参或随返回值带出复用（写原语直接交出已确定生成值）；进入列表/分页循环前先批量预取；循环不变量、预编译正则与静态常量索引提到循环外或模块加载期；嵌套区间交集查询用静态中点区间树；展示筛选只读预计算读模型。
- **例子**：`#80` 路由先调 `service.preview_export()`，下一行又穿透调私有 `service._states_and_rows()` 把同样的查库重跑一遍；`#15` 先 `find_by_request_key()` 拿 `job_id`，下一行再 `get_status(job_id)` 查同一条记录。

#### H. 缓存失效
- **识别信号**：缓存键混入每行唯一 ID 或与结果无关的可变字段（命中率 0%，或改一行全盘失效），或快照指纹卷入整份派生大结果、公共目录正文与未跟踪运行副产物；以 `id(obj)` 为键却在热路径每轮 `copy(obj)`，或在读模型入口跑 `encode(decode(raw))` 重格式化因键序/空白差异反向打穿上游原始文本缓存键；查缓存写在全量读取或深拷贝之后，或命中后仍无条件重跑全量扫描、归一化与排序；外层派生缓存与底层加载缓存分头维护失步（外层恒返 `None`），或多分支加载某分支漏挂缓存并被下游 `=None` 静默重算掩盖；用 `or` 判缓存命中把合法 `0`/`[]` 当缺失；缓存异常实例后多次裸 `raise cached_exc` 导致 `__traceback__` 栈帧成倍累积（公开出口泄漏缓存可变引用见母题 M）。
- **正确做法**：缓存键与指纹只绑定真正决定结果的源头版本与查询边界；先查缓存再读库，命中即短路；缓存归一化后的成品，二级索引内聚在唯一事实源对象中原子更新；判命中用 `is not None` 或 `key in cache`；重抛缓存异常前 `.with_traceback(None)` 清栈帧。
- **例子**：`#65` `window_key = (task_id, start_dt, due_dt)`，每条任务一个键，5,000 条任务命中率恒为 0%；`#83` 命中去重缓存后，仍对 5,000 个结果对象全量扫描、排序、重新归档。

#### I. 偷偷传状态
- **识别信号**：把数据挂在函数对象属性上，或从外部往别人的服务、快照实例上动态塞 `_private` 属性偷渡数据，下游再用 `getattr(..., None)` 探测并配重算兜底；在服务或仓储实例上临时改属性传参、`finally` 里置空还原；从模块级全局字典取值后原地 `.update(...)` 造成跨请求污染，或在业务层建临时表充当进程内存缓存；往纯数据字典里塞带连接的服务/仓储实例（把查库偷渡进纯投影层），或继承内置 `dict` 覆写 `__getitem__` 在读键时暗藏 SQL 查库与自改写；只读准入/校验/投影函数顺手原地改写或 `.pop()` 调用方传入字典，两个视图共享同一批可变 dict 靠原地改写“顺带”联动，或在 `@property.setter` 里暗藏同步副作用。
- **正确做法**：用显式参数、返回值或 dataclass 传递数据；状态变更走唯一正规入口；只读准入与投影保持 100% 纯只读；不同视图各自构造输出字典，不靠共享可变容器隐式联动。
- **例子**：`#29` 在 `with service.read_snapshot():` 里偷偷给 `self.active_codes` 赋值，`finally` 又置回 `None`，逼调用方在退出前“抢救”；`#96` 调用前写 `repo.report_revisions = ...`，调用后在 `finally` 里清空。

#### J. 口径没在源头统一
- **也涉及**：拷问 4（平行链路横向分叉，违背《认知一致性》“同一件事只有一条路”）。
- **识别信号**：同一领域规则在多个平行入口（表单 vs 导入、摘要 vs 完整模式、运行时命令探测 vs 门禁指纹、多处路由横切响应头）各写一套或写 `# Mirrors ...` 镜像维护，或外部子进程选型与运行时规避标志不在唯一入口收口而在个别测试散打命令行补丁；预览与提交、大小预算丈量（宽松 `json.dumps`）与实际落库（紧凑 `canonical_json`）、写侧准入值域与读侧解析值域、生产连接与测试夹具（如数据库类型转换器开关）各算一套导致行为分叉；把共用基础校验藏进只处理局部子态的下游 helper 造成其他子态漏检，或把未准入数据的静默排序/修补混进只读加载入口；把“新建录入禁首尾空格”的清洗规则误套到按永久主键读取/维护存量实体的链路上；外部输入只做表层字符检查就甩给宽松标准库，导致跨版本行为分裂或超长输入崩溃；把完全由源字段决定的纯派生值存成可写字段（`replace()` 后失步），把公开已舍入展示值回流充当内部计算/排序输入，或上游有现成因子却只存乘积逼下游除法反推；上游缺字段在下游手写推导式补，调用方自行切片绕过契约上限，加 `strict_*=False` 双轨开关，或把两个不同时机的职责塞进一个返回元组的 `Optional` 函数再靠三元表达式互绕。
- **正确做法**：规则、值域、子进程选型与格式不变量抽到唯一领域函数或共享边界，所有入口、读写两侧、预览/提交、运行时/测试夹具共用同一实现；新编号规范化只归创建/导入入口，按永久主键读取维护全链路保真原值；纯派生值做成只读 `@property`；上游缺什么回上游补，一个函数只担一责。
- **例子**：`#55` “非工作日必须清空工作时段、配额设为 0”在详情表单里写一套，在电子表格导入里又拆成两段写一套；`#75` 导入预览算出一套目标集合，提交时却不消费预览结果、按行序重新算。

### 拷问 3：把内部结构当外部输入防（防错了地方）

#### K. 吞错与静默降级
- **也涉及**：拷问 4。
- **识别信号**：内部受控计算外包宽泛 `except (KeyError, TypeError, ValueError, ...)`，外层宽泛捕获误吞解析钩子抛出的业务拒绝异常，底层已有异常契约外层再套一层 `try`，或同函数内自抛自接；对受控字典或 `from_row` 缺键吞 `KeyError` 回退旧状态/默认值（掩盖 SQL 漏列），对上下游未定型字典用 `.get()` 把键名拼写错配静默吞成常年 `None` 假空态，或 `NOT NULL` 存储列解析配 `default` 与 `errors="ignore"` 把损坏字节静默读成合法值；上一行先塞默认值兜底，下一行再写永不可达的 `if x is None: raise` 架空必填校验；上下文损坏时降级成 `None` 反而绕过针对它的业务限制，或用正向类型白名单 `isinstance(...) else None` 把意外类型脏数据静默洗白成空值绕过准入校验；把锁文件读取 `OSError` 与内容过期混同触发自愈误删活跃锁（Fail-Open），停止屏障超时后忽略超时继续写盘，`finally` 关闭失败直接 `raise` 顶掉 `try` 块已拿到的结果，或进存量结构守卫前先对未验脏行排序让裸 `TypeError` 抢跑炸穿结构化诊断。
- **正确做法**：`try` 只包解析外部输入或存储字节的最小单语句，只捕精确异常；内部结构定型并直接按键/属性访问，让键名错配或 `KeyError`/`TypeError` 当场暴露；`NOT NULL` 列与必填校验直面未兜底原始输入，脏数据先进结构守卫明确拒绝；I/O 读取异常走 Fail-Closed。
- **例子**：`#47` `group = None if problem else build_group(context)`：上下文越坏，后面的 `if group and group["mode"] == "merged": raise` 越管不住；`#18` `parse_hhmm(..., allow_none=False)` 缺失时静默返回 `"08:00"`，下一行的 `if start is None: raise` 永远进不去。

#### L. 删旧壳时搬家兜底
- **说明**：编码模型（尤其是 GPT）被要求删防御或过门禁时最常见的反扑，审 diff 时重点盯下层被调函数与被搬动模块。
- **识别信号**：要求删掉上层吞错、布尔开关、`getattr` 探测或包装壳后，diff 里下层函数反而新冒出 `try/except`、`.get()`、`or default`、`Optional = None`，或在下层对本文件刚算出的受控有界值塞入 `isinstance` 与 `OverflowError` 事后自我怀疑；不敢统一口径，新加 `strict_*=False`、`_prevalidated=False` 双轨开关，或把已删的上层开关塞进下层 helper 捆成双职责函数、复制旁路模块挂闭包守卫树；为应付门禁棘轮搞“症状搬家”：不拆混居职责而把顶层 `import` 塞进函数体内变延迟导入环（甚至让下层仓储反向导入上层服务），或不查调用链死活把上层 0 触发死分支里的 SQL 抽成底层新仓储方法；子类或测试夹具漏初始化必填属性，不在源头补齐，反而在基类写 `if self.attr is not None` 配 `cast(...)`；拆分或搬迁函数时把旧代码的宽泛 `except` 原封不动抄进新函数。
- **正确做法**：删兜底就是真删，按上游契约直接 `payload["key"]`、`obj.attr`；规则直接收口为单一严格口径；拆导入环必须按职责层级物理拆分模块，禁拿函数内延迟导入糊弄；缺的初始化补在子类或测试夹具；拆迁函数按新函数体重新核定真正可能抛出的边界异常。
- **例子**：`#27.1` 删掉上层 1 处宽泛 `except`，下层 5～7 个函数各塞一套，1 处吞错裂变成 7 处；`#44` 删掉包装模型后，在仓储里写 `payload.get("status") or "active"`，而唯一调用方早已传入完整字典。

#### M. 无用拷贝与往返转换
- **也涉及**：拷问 2（含可变容器所有权边界）。
- **识别信号**：对不会被原地修改的受控数据做 `.slice()`、`list()`、`dict()`、`deepcopy()`、`asdict()`、`clone_json()`，对受控标量反复套同类型强转，仓储已返新 `dict` 上层再套 `[dict(row) ...]`，或上游构造器无脑浅拷贝替下游某处原地修改擦屁股；可变所有权边界错位（“内部瞎拷、出口裸奔”）：内部只读投影/校验链对缓存归档层层深拷贝，而公开 DTO 出口反而漏做隔离直接裸返全局缓存可变列表/字典（或仅新建外层字面量、内层直挂缓存可变子对象）；类型与序列化乒乓往返：刚解析成强类型（`datetime`、领域对象、已解析字典）立刻 `.isoformat()`/`.to_dict()` 转回字符串或字典让下一层重解析，用 `json.loads(json.dumps(x))` 当深拷贝或比对字典相等，只读加载跑 `encode(decode(raw))`，或同一子树塞进顶层与子字典做双倍序列化；精确整数、微秒时间差或有理数容量中途绕道 `float` 分段累加/相减，造成 `> 2^53` 精度截断或 `±1e-16` 浮点漂移。
- **正确做法**：入口解析一次，内部全程传强类型对象，仅在输出边界序列化一次；精确整数、时间差与有理数全程用 `int` / `Fraction` 运算；内部只读链共享缓存引用，仅在公开 DTO 出口或可变草稿边界做唯一一次隔离复制；谁转换字段谁生成新字典。
- **例子**：`#11` `parse_dt` 的结果立刻转成字符串返回，下一层算分钟差再 `fromisoformat()`；`#152` 内部只读投影层层防御深拷贝，公开时间线 DTO 出口却把全局缓存里的可变列表裸返给调用方。

### 拷问 4：意思被改了（做错了）

> 这一组和前三组方向相反：问题不是多做，而是做错。删防御、做统一时最容易顺手踩中，也最容易被误当成“过度防御”删掉。

#### N. 事务、锁与状态生命周期
- **也涉及**：拷问 2。
- **识别信号**：写锁或写事务内做文件 I/O、重型报表/大 JSON 哈希或逐行 N+1 查询；外层已持事务或 `read_snapshot` 读快照，内层循环或只读方法又套 `with transaction(conn):` 开嵌套 `SAVEPOINT`；同一业务视图的关联数据脱离主读快照事后另开查询拼凑造成跨时间点撕裂；纯读入口（如 `read()` 或模块 `import` 顶层）暗藏锁外写盘补刷、隐式连正式库建表或注册全局退出钩子，或暂存延迟写入时丢弃前置附属回调；前置校验失败或中途抛错却留下预设的终态标志、锁或半截共享列表；删锁、删存活实例契约文件、杀进程等破坏性动作先于参数与运行锁活跃性核验，或单任务失败恢复误调全表清理；把服务端已确认终态后的本机存储写/删异常混进网络 `try/catch` 篡改成未决态，异步轮询在挂起窗口晚到冲掉用户脏草稿，或清理失败时仅在组件局部 `useState` 存终态导致重挂载复活无效轮询；会话/计划切换只重置一半状态，异步查询混用“防闪烁过渡展示旧值”与“匹配当前身份的真值”导致刷新或失败时导出/提交上一对象旧数据，按需加载标志未绑定当前结果身份，唯一解锁出口藏在未挂载/被遮挡组件，或表单下拉框用静态 `index === 0` 焊死 `disabled` 锁死首行删除后的纠偏出口；`except BaseException` 误捕 `StopIteration` 或 `except Exception` 漏捕 `GeneratorExit` 导致不回滚。
- **正确做法**：事务与锁边界只归一处，锁内只做最小必要工作，批量写入共享外层事务，关联读取同属一个读快照；纯读入口零写副作用；失败、取消、完成的每条分支对称复位状态；严格分离服务端命令终态与本机存储状态、分离过渡展示值（`shown`）与业务动作消费的当前身份真值（`result`）；先验参数与锁再做破坏性清理；子会话状态与会话身份同生共死。
- **例子**：`#79` 恢复在前置检查阶段失败、原库没动，却没复位预设的 `restart_required=True`，宿主永久 503；`#49` 批量入口已开事务并查过表结构，循环里每行又调单条入口再开嵌套事务重查。

#### O. 语义走样
- **识别信号**：
  - **假值与空态误伤**：用 `or` 合并合法的 `0`、`[]`、`""`；在未加载或不可用态下用 `0 == 0` 误判“已完整加载”或把未知数量渲染成 `"0"`；稀疏更新把“显式传 `None` 清除值”与“省略键保持原值”混为一谈，或用 `None` 兼任未传参哨兵掩盖存储损坏读出的 `null`；用陈旧非空信号遮蔽存活信号。
  - **校验与过滤顺序颠倒**：类型校验或归一化之前先用 `==`/`!=` 过滤未改字段（放行 `True == 1`）；推导式里把业务子集过滤写在字段合法性校验前面，放跑被筛掉的脏记录；先验全量输入再 diff 误拒未改旧字段；先生成派生快照再分配新主键，或校验前用待测数据改写校验基准。
  - **源头保真与边界失守**：为防下游个别比值除零，在特征源头把合法 `0.0` 篡改成 `epsilon` 连坐污染全局排序与传播；读取或按永久主键维护既有实体时做 `.strip()` 把 `" B1 "` 串线到 `"B1"`；重抛结构化异常只改顶层 `field` 却原样透传旧 `details["field"]`；正常业务边界混入“数据损坏”标记；仅凭物理 `integrity_check` 放行 0 表空备份库；高权限执行用窄路径黑名单代替受控来源/写权限白名单。
  - **精度与阈值错配**：用 `float` 容差近似代替 `Decimal` 精确整数解析；在下游用 `max(0.0, ...)` 单向夹断掩盖负浮点漂移却放行假正残差；用有限位 `Decimal` 比较 `1/3` 等循环小数严格阈值；拿业务显著性阈值去做结构存在性判定。
  - **维度与时间基准压缩**：用 `segments[0]` 或首尾包络代替多段区间；零时长点事件混入区间重叠公式或被 `end <= start` 一刀切拒绝；用局部切片代替完整关系闭包做依赖校验，或缩小日期窗口查询误套全图上限；后台异步执行不复用受理归档快照而重调挂钟时间导致跨午夜漂移；模式切换沿用旧模式同值过滤；序列出口去重却不推进游标与预算计数。
- **正确做法**：判断“已提供”用 `is not None`，严格区分“省略键”与“显式 `None`”；先全量验类型与合法性，再做业务过滤或 diff；写入口严防、读与按永久主键维护侧保真；源头保留真实 `0` 与精确有理数/整数，展示或局部公式各自处理边界；多段保持多段，闭包校验取完整闭包，异步执行消费受理快照；执行信任边界走受控白名单。
- **例子**：`#94` 类型校验前写 `{k: v for k, v in values.items() if v != raw[k]}`，库存为 `1` 时上传 `TRUE` 被当成“没改”绕过布尔拒绝；`#91` 底层“防御性” `.strip()` 把对 `" W1 "` 的读写串到 `"W1"` 头上。

## 四、怎么用与入库规则

### 1. 怎么用
- 每处设计与改动先过 **4 条第一性原理拷问**，再对照 **15 个母题**的识别信号过筛。
- 删防御之前，必过**拷问 4** 和 **N、O 两个母题**，确认删掉的不是真实的业务保护（快照一致性、完整关系闭包、存量身份保真、状态对称复位等）。
- 审 `git diff` 时必须同时审 `tests/` 的 diff（母题 D）。
- 具体案例以 [blacklist-cases.md](blacklist-cases.md) 每条标题下的 `> 母题：` 标签为**唯一事实源**（主表不手抄全量案例编号）；需查阅某母题历史战例时，按需检索 `rg "^> 母题：.*<A-O>" references/blacklist-cases.md -B 1` 或按 `#编号` 定点查看。

### 2. 入库规则（严格控重、主表稳态）
审查或复核抓到反模式时，先当场剥离修复，再按以下门槛决定是否入库：
1. **老套路换马甲不入库**：若只是已有母题和案例早已覆盖的同构写法换了个业务模块、表名或字段名，直接修代码结案，**不再往案例库追加同质化新号**。
2. **仅新结构花样才立新号**：只有撞见现有案例库未曾记录的**新型代码结构套路**时，才在 [blacklist-cases.md](blacklist-cases.md) 末尾顺延编号（历史编号永久不变），并在标题下标注 `> 母题：<主母题> [· <副母题>]`。
3. **底层工具/平台 API 坑点分流**：纯粹属于特定数据库方言、操作系统、运行时或打包工具的 API 用法备忘（非通用过度防御或架构反模式），优先记入对应项目的注意事项文档（如 `AGENTS.md` / `attention.md`），不塞进跨项目通用的主表识别信号。
4. **主表默认不动**：新增案例只要能被现有母题的抽象识别信号罩住，**主表一字不改**；仅当暴露出全新的跨项目抽象代码形态时，才用**不含具体业务名词**的短句凝练补入对应母题；所有母题都归不进才讨论新开母题，发现母题重叠则合并。
5. **一条一事**：一条案例只写一种结构花样；同一轮审查抓到的多件独立问题若确需入库必须拆条单列，严禁把互不相干的问题用“或 / 以及”硬缝成一条。
